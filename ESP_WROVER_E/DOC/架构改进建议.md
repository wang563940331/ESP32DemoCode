# ESP_WROVER_E 架构改进建议

> 基于当前代码结构，从设计模式与分层架构角度整理的优缺点分析与改进方向。  
> 生成日期：2026-08-27

---

## 一、整体架构概览

项目采用典型的 **ESP-IDF 分层组件**结构：

```
main（启动编排 + LED 状态机）
  ├── APP（业务逻辑：网络、电表、传感器、SD 日志、LED 效果）
  └── BSP（板级驱动：UART/GPIO/ONE_WIRE/参数/Shell/内存池）
```

| 层级 | 职责 | 主要模块 |
|------|------|----------|
| **main** | 系统入口、初始化顺序、主循环 | `main.c`、`app_config.h`、`version.*` |
| **APP** | 业务逻辑 | WIFI_STA/AP、MQTT、JSON、METER、SENSOR、SD_FAT、LED |
| **BSP** | 硬件抽象与基础设施 | UART、GPIO、ONE_WIRE、PARAM、SHELL、UTILITY |

## 二、已体现的设计模式评价

### 2.1 工厂方法 + 策略模式（C 语言 vtable）

**涉及模块**：`gpio_output_bsp`、`uart_bsp`、`one_wire_bsp`、`sd_fat_bsp`

通过函数指针结构体（如 `gpio_output_device_t`、`uart_device_t`）实现多态，配合配置映射表 + `factory_get_device()` 获取实例。

| 优点 | 缺点 |
|------|------|
| 硬件与业务解耦，换引脚/协议只改映射表 | 实际多为单实现，策略能力未充分利用 |
| C 语言下风格统一，可 mock | `factory_init` 调用不一致（有的模块直接 `get_device`） |
| 符合开闭原则 | 配置硬编码在 `.c` 里，缺少 Kconfig 式配置 |

### 2.2 适配器模式

**涉及模块**：`uart_bsp.c`（RS485 / TTL）

`uart_protocol_adapter_t` 隔离协议差异，`uart_device_t` 保持统一对外接口，职责分离清晰，是项目中设计最佳的一处。

### 2.3 门面模式

**涉及模块**：`sd_fat_ops`、`parameterSet`

- `sd_fat_ops_t` 封装底层 FAT 操作
- `parameterSet` + `g_stParamConfig[]` 统一 NVS/cJSON 读写

### 2.4 命令模式

**涉及模块**：`shell.c` / `shell.h`

各模块通过 `sShellCmdRegister()` 注册命令，调试友好，但命令注册分散，缺少统一目录。

### 2.5 生产者-消费者 + 对象池

**涉及模块**：`sensor_task`、`meter_DLT645`、`mqtt`、`sd_fat_log_task`、`memory_pool`

FreeRTOS 任务分工 + PSRAM 预分配，适合嵌入式实时场景。

### 2.6 依赖注入（局部）

**涉及模块**：`sd_fat_log_task_init(config, ops)`

`main.c` 注入 `sd_fat_ops_t` 指针，解耦较好，可推广到其他模块。

### 2.7 隐式单例

**涉及模块**：`g_sensor_data`、`g_meter_data`、`s_mqtt_client`、`stNvsCache`

访问简单，但模块间隐式耦合，多任务读写存在线程安全风险。

## 三、架构层面优缺点

### 3.1 优点

1. **分层清晰**：BSP 不依赖 APP，硬件抽象集中在工厂层
2. **工厂 + 函数指针** 是 C 嵌入式成熟方案，可移植、可 mock
3. **UART 适配器** 职责分离明确，注释与实现一致
4. **任务拆分方向正确**：sensor 已从 mqtt 独立，meter 有独立任务
5. **参数系统表驱动**：`stParamConfig_t` + `rebootAction` 有扩展性
6. **编译期配置**：`app_config.h` 控制传感器类型、日志开关等

### 3.2 缺点

#### 问题 1：组件循环依赖

```
APP/CMakeLists.txt  → REQUIRES main
main/CMakeLists.txt → REQUIRES APP
```

违反分层依赖方向，通常因 APP 引用了 `main` 或 `app_config.h`。

#### 问题 2：MQTT 模块接近「上帝对象」

`mqtt.c` 同时负责：连接管理、JSON 组包、电表/传感器上报、电量历史环形缓冲、NVS 持久化、SNTP 同步。违反单一职责。

#### 问题 3：缺少显式状态模式

`main.c` 主循环用 `if-else` 链决定 LED 状态；网络生命周期分散在多个 getter 中，缺少 FSM。

#### 问题 4：模块间靠共享全局变量集成

```c
extern SensorData_t g_sensor_data;  // sensor_task.h
extern MeterData_t  g_meter_data;   // meter 模块
```

缺 Observer / Data Service，后续加 BLE/Web 上报会重复逻辑。

#### 问题 5：头文件「胖依赖」

`uart_bsp.h`、`mqtt.h`、`shell.h` 等包含大量 WiFi/MQTT/NVS 头文件，违反接口隔离，编译耦合重。

#### 问题 6：工厂初始化不一致

- LED/蜂鸣器：先 `factory_init` 再 `get_device` ✅
- sensor：直接 `one_wire_factory_get_device`
- UART2：main 里 init，UART1：meter 里 init

缺少统一的 Board Init 门面。

#### 问题 7：SD_FAT 分层归属混乱

`sd_fat_bsp`（工厂+驱动）在 APP 组件，按惯例应在 BSP，APP 只保留日志业务。

## 五、改进建议（按优先级）

### P0 — 打破 main ↔ APP 循环依赖

**现状**：`APP` 组件 `REQUIRES main`，`main` 又 `REQUIRES APP`。

**方案**：新建独立组件 `common`（或 `config`），迁移：

- `app_config.h`
- `version.h` / `version.c`

**目标依赖关系**：

```
main  → APP, BSP, common
APP   → BSP, common
BSP   → common（如需要）
```

**改动文件**：

- 新建 `components/common/CMakeLists.txt`
- 修改 `components/APP/CMakeLists.txt`：去掉 `main`，改为 `common`
- 修改 `main/CMakeLists.txt`：增加 `common`

---

### P1 — 引入轻量 Event Bus（观察者模式）

**现状**：`mqtt.c` 直接 `#include "sensor_task.h"` 并读 `g_sensor_data`。

**方案**：在 `BSP/UTILITY` 或新建 `common/event_bus` 提供发布-订阅：

```c
/** 事件类型 */
typedef enum {
    EVENT_SENSOR_UPDATED,
    EVENT_METER_UPDATED,
    EVENT_MQTT_CONNECTED,
    EVENT_MQTT_DISCONNECTED,
    EVENT_MAX
} event_type_t;

/** 订阅回调 */
typedef void (*event_handler_t)(event_type_t type, const void *data, size_t len);

/** 订阅事件，返回句柄供取消订阅 */
int event_subscribe(event_type_t type, event_handler_t handler);

/** 发布事件（拷贝或指针传递，由约定决定） */
void event_publish(event_type_t type, const void *data, size_t len);
```

**迁移步骤**：

1. `sensor_task.c` 读取成功后 `event_publish(EVENT_SENSOR_UPDATED, &g_sensor_data, sizeof(...))`
2. `meter_DLT645.c` 解析成功后发布 `EVENT_METER_UPDATED`
3. `mqtt.c` 订阅上述事件，组包上报，不再 `#include sensor_task.h`

---

### P1 — 拆分 mqtt.c

**建议模块划分**：

| 新模块 | 职责 | 原 mqtt.c 中的内容 |
|--------|------|-------------------|
| `mqtt_transport.c` | 连接、重连、订阅、发布底层 API | `esp_mqtt_client_*` 封装 |
| `mqtt_payload.c` | JSON 组包/解包、主题路由 | `parse_json`、上报 JSON 构建 |
| `energy_history.c` | 电量环形缓冲 + NVS 持久化 | `EnergyDailyHistory_t` 相关 |
| `data_reporter.c` | 聚合 sensor/meter/energy，调用 transport 发布 | MQTT 任务主循环中的上报逻辑 |

**原则**：`mqtt_transport` 不感知 sensor/meter；`data_reporter` 通过 Event Bus 或回调获取数据。

---

### P2 — 统一 Board Init 门面

**现状**：`app_main()` 中 200+ 行初始化，多处 `mdf_mem_print_heap()`。

**方案**：新建 `board_init.c`（放 BSP 或 main）：

```c
typedef struct {
    bool enable_sd_log;
    bool enable_meter;
    bool enable_sensor;
} board_init_config_t;

/** 按固定顺序初始化所有外设工厂与基础服务 */
esp_err_t board_init(const board_init_config_t *cfg);

/** 初始化网络栈（netif / event / wifi） */
esp_err_t board_init_network(void);

/** 初始化业务任务（mqtt / meter / sensor） */
esp_err_t board_init_app_tasks(void);
```

**`app_main` 简化为**：

```c
void app_main(void) {
    board_init_config_t cfg = BOARD_INIT_DEFAULT();
    board_init(&cfg);
    board_init_network();
    board_init_app_tasks();
    board_run_led_state_machine();  // 或独立任务
}
```

---

### P2 — 网络/LED 有限状态机（FSM）

**现状**：`main.c` 中：

```c
if (gets_is_smartconfig())       led_blink();
else if (get_ap_connected())     led_fast_blink();
else if (!gets_is_mqtt_connected()) led_heartbeat();
else                             led_breath_heart();
```

**方案**：

```c
typedef enum {
    SYS_STATE_SMARTCONFIG,
    SYS_STATE_AP_CLIENT,
    SYS_STATE_MQTT_CONNECTING,
    SYS_STATE_MQTT_ONLINE,
} system_state_t;

/** 根据当前网络状态计算系统状态 */
system_state_t system_state_evaluate(void);

/** 按状态驱动 LED 表现 */
void led_apply_state(system_state_t state);
```

可进一步用**状态转移表**替代嵌套 if-else，便于单元测试与日志追踪。

---

### P3 — BSP 头文件瘦身（接口隔离）

**原则**：BSP 头文件只暴露本模块类型与 API，不包含 WiFi/MQTT/NVS。

**示例**：`uart_bsp.h` 当前包含 `esp_wifi.h`、`mqtt_client.h` 等，应移除，仅保留：

```c
#include "driver/uart.h"
#include "esp_err.h"
```

WiFi/MQTT 相关依赖移到 APP 层对应模块。

---

### P3 — SD_FAT 归位到 BSP

**建议结构**：

```
components/BSP/SD_FAT/
  ├── sd_fat_bsp.c/h    # 工厂 + 底层挂载
  └── sd_fat_ops.c/h    # 门面接口

components/APP/SD_FAT/
  └── sd_fat_log_task.c/h  # 仅日志业务
```

APP 通过 `sd_fat_ops_t` 访问，不直接依赖 bsp 实现细节。

## 六、推荐实施路线图

```
阶段 1（1~2 天）
  └── 新建 common 组件，消除 main↔APP 循环依赖

阶段 2（3~5 天）
  ├── 实现 Event Bus 最小版本
  ├── sensor/meter 改为 publish，mqtt 改为 subscribe
  └── 拆分 energy_history 出 mqtt.c

阶段 3（3~5 天）
  ├── 拆分 mqtt_transport / mqtt_payload / data_reporter
  ├── board_init 门面统一初始化
  └── LED + 网络 FSM

阶段 4（可选）
  ├── BSP 头文件瘦身
  └── SD_FAT 组件归位
```

## 八、总结

当前架构在 **BSP/APP 分层、工厂+策略、UART 适配器、参数表驱动、任务拆分** 上已具备较好的嵌入式工程化基础。

主要短板是：**模块间靠全局变量和 mqtt 大模块粘合**，以及 **main↔APP 循环依赖**、**缺少事件/状态两类协调模式**。按本文 P0→P3 顺序逐步改造，可在不推翻现有代码的前提下显著降低后续功能扩展的耦合成本。
